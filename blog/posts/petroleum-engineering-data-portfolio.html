How to present a petroleum data project

A strong project page is more than a tool list. It explains the engineering question, makes the data and method inspectable, and tells the reader what still needs validation.

AOSAbdirahman Osman SiyadPetroleum Engineer & Data Analyst · 5 min read

Petroleum engineering and analytics projects can be difficult to explain to someone who has not seen the source data. A useful portfolio entry gives the reader enough context to assess the work without asking them to guess what was done or what the results mean.

Lead with the question

Write one sentence describing the problem the work addresses. “I used SQL” is a method, not a problem statement. A more useful framing might explain that the project organizes daily records into candidate operating intervals for review. Keep the scope as narrow as the work itself.

Explain the data before the tools

State where the data came from, what date range or record types it covers, and what each row represents. If the dataset is public, link to it. If it is confidential, describe its structure without exposing restricted information. Note missing fields, assumptions, and any data that was unavailable.

Show the method in reviewable steps

Break the work into stages a reader can follow. For a database project, that might be:

  1. Load source records and preserve the original fields.
  2. Standardize values using documented rules.
  3. Check keys, duplicates, and expected ranges.
  4. Apply the analytical query or engineering screen.
  5. Review representative cases against the source records.

Link to the relevant code and explain the purpose of the important transformations. Avoid dumping a repository link without pointing to the file or explaining what a reviewer should look for.

Separate outputs from interpretation

Describe what the code produced and what an engineer can reasonably conclude from it. A grouped set of dates, for example, may identify candidate periods for review; that alone does not establish a physical event or an engineering diagnosis. Use language that matches the actual validation performed.

If you report numerical results, show how they were calculated and make sure they can be reproduced from the published data and code. If you have not run a query against the stated source, describe it as a proposed workflow or example rather than a measured finding.

Make the page easy to scan

Use a short summary, a small workflow diagram or screenshot where it clarifies the method, links to the repository, and a concise “limitations and next checks” section. A reader should be able to find the project purpose and evidence quickly on both a phone and a desktop screen.

A practical project outline

  • Question: What decision or workflow does this address?
  • Data: What is the source, grain, and known limitation?
  • Method: What transformations and checks were applied?
  • Evidence: What output can be reproduced or inspected?
  • Limits: What does the result not establish?
  • Next step: What additional data or review would improve confidence?

Clear project writing is part of the engineering work. It helps another person judge the method, spot assumptions, and decide whether the result is useful for their context.

Portfolio rule: Do not invent business impact, measured outcomes, or technical certainty. A precise description of a limited workflow is more credible than a broad claim the evidence cannot support.
