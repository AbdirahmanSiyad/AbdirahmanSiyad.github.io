A practical SQL checklist for production data quality

A reliable analysis starts before the chart or model. These checks help surface the data issues most likely to distort a well-level production view.

AOSAbdirahman Osman SiyadPetroleum Engineer & Data Analyst · 6 min read

Production records can look tidy while still hiding duplicate reporting days, incomplete identifiers, or measurements that violate the rules of the source system. A few repeatable checks in SQL make these issues visible before they reach a dashboard.

The examples below assume a table called daily_production with a well identifier, a reporting date, and three measured volumes. Replace the table and column names with your own, and confirm the source definitions and units first.

1. Agree on the record grain

Write down what one row is supposed to represent. For this example, the intended grain is one record per well per reporting date. If a well can have multiple streams, facilities, or tests on the same date, include that dimension in the grain instead of treating valid records as duplicates.

2. Find missing identifiers and dates

SELECT *
FROM daily_production
WHERE well_id IS NULL
   OR production_date IS NULL;

These are often unusable for time-series analysis because the record cannot be assigned confidently to a well-day. Don’t automatically discard them; first find out whether the source has a correction path or a separate identifier field.

3. Check uniqueness at the agreed grain

SELECT well_id, production_date, COUNT(*) AS row_count
FROM daily_production
GROUP BY well_id, production_date
HAVING COUNT(*) > 1
ORDER BY row_count DESC, well_id, production_date;

This query flags duplicate keys for the example grain. A duplicate may be a load issue, a legitimate split record, or evidence that the grain was defined too narrowly. Investigate before choosing a rule to combine rows.

4. Test business rules, not guesses

If the source contract says reported volumes cannot be negative, test that rule explicitly:

SELECT *
FROM daily_production
WHERE oil_volume < 0
   OR water_volume < 0
   OR gas_volume < 0;

This is only appropriate if those columns are defined as non-negative reported volumes. Adjust the test for the actual meaning of each field; a negative value might be a valid adjustment in some systems. Also distinguish a zero from NULL: zero is a recorded value, while NULL means the value is absent or unknown.

5. Look for missing reporting dates

A missing date is not automatically a shut-in. First establish which wells should report on which days, and decide how to represent non-reporting days. Then compare expected well-date combinations with observed records. Keep an explicit status such as “not reported” separate from measured zero production.

6. Keep checks repeatable

For each check, record the rule, the number of records flagged, the data period, and whether someone reviewed the exceptions. A practical sequence is:

  1. Confirm source definitions, units, and row grain.
  2. Run required-field and uniqueness checks.
  3. Check allowed ranges and valid status values.
  4. Compare observed dates with the expected reporting calendar.
  5. Review flagged records with someone who understands the source.

These queries do not prove that the data is correct. They make assumptions testable and exceptions visible, which is a much stronger place to begin analysis.

Important: The SQL here is illustrative. Validate column definitions, units, reporting rules, and database behavior against the actual source before using it operationally.
