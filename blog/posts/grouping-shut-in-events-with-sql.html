Grouping candidate shut-in periods with SQL

A gaps-and-islands pattern can turn daily status rows into candidate continuous events. The key is to group explicit status data, not infer an event from a convenient zero.

AOSAbdirahman Osman SiyadPetroleum Engineer & Data Analyst · 7 min read

Daily operational tables are easier to inspect when consecutive status days are summarized into one interval. In MySQL 8, a window function can assign each qualifying date a row number. Subtracting that row number from the date creates a shared key for consecutive days.

This example assumes a table with one row per well per calendar date and an explicit operating_status value. The permitted status values and their meaning must come from the source system, not from assumptions made in a query.

Start with explicit status

Suppose the source marks days as SHUT_IN or another operational status. First select only the explicit shut-in rows and collapse any accidental duplicate well-date entries. If duplicates have different statuses, resolve that data-quality problem before grouping.

Number the dates, then identify islands

WITH shut_in_days AS (
    SELECT well_id, production_date
    FROM daily_status
    WHERE operating_status = 'SHUT_IN'
    GROUP BY well_id, production_date
), numbered_days AS (
    SELECT
        well_id,
        production_date,
        ROW_NUMBER() OVER (
            PARTITION BY well_id
            ORDER BY production_date
        ) AS day_number
    FROM shut_in_days
), islands AS (
    SELECT
        well_id,
        production_date,
        DATE_SUB(production_date, INTERVAL day_number DAY) AS island_key
    FROM numbered_days
)
SELECT
    well_id,
    MIN(production_date) AS candidate_start,
    MAX(production_date) AS candidate_end,
    COUNT(*) AS consecutive_status_days
FROM islands
GROUP BY well_id, island_key
ORDER BY well_id, candidate_start;

For consecutive calendar dates, the date and row number advance together, so DATE_SUB(date, INTERVAL row_number DAY) stays constant. A gap changes that key and starts a new group. The result is a list of contiguous intervals, not a diagnosis of why the well was shut in.

Validate the boundaries

Before relying on the output, check the source grain, timezone or date convention, and status history. Inspect sample wells that cover a continuous run, a one-day gap, a duplicate date, and a status change. Compare the grouped dates back to the original records.

  • If the status is inferred from volume, define the threshold and its units with an engineer first.
  • If the data has missing dates, decide whether a gap breaks the interval; this query treats it as a break.
  • If events must be separated by a minimum duration, add that as a documented screening rule after grouping.

What this does not establish

Grouping status rows is a data-preparation step. It does not show that a pressure build-up is suitable for analysis, establish a pressure response, or replace pressure-transient interpretation. Any later engineering workflow needs the relevant measurements, metadata, units, quality controls, and review.

Scope: This pattern is for first-pass event grouping using explicit daily status. It is not a full PTA workflow and is not a substitute for validating field definitions and candidate events.

When the rules are explicit, window functions make the grouping reproducible and easy to audit. That is a useful outcome on its own: a reviewer can see exactly which dates formed each candidate interval and why.
